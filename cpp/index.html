kladde-cpp

kladde-cpp

Oct 15, 20266 min read

The C++ implementation of kladde: one of the two reference implementations of the specification, independent of kladde-rs in Rust, and the library behind the Inkscape demo.

Everything here is specific to C++. The file format and the algorithms are shared with kladde-rs; the description of types, the handles and the error handling are not. Its design was worked out in the C++ draft, which this section records as built, with the places where building it went another way.

What it is

A CMake project, C++20, with no required dependencies: a compiled schema layer and store, and a header-only typed layer on top.

Three layers

the schemakladde/schema.hppdescriptors, their canonical encoding, fingerprints, sizes, and a textual dump for comparing tables across implementations

typed valueskladde/kladde.hppwhich C++ types are durable, how they encode, their handles, and kladde::File

The store and the schema are compiled into kladde::kladde; the typed layer is templates over a small virtual interface, kladde::Backend, which the store implements and which a kladde::VectorBackend — a plain byte vector that applies every mutation at once — implements for tests.

Which C++ types are durable

Standard types are durable wherever the in-memory value needs nothing a standard type cannot hold, and kladde’s own containers take over where it does.

Text must be UTF-8. A std::string used as a byte buffer — file contents, a serialized message, a binary identifier — is not text, and storing one fails; hold bytes in a std::vector<std::uint8_t>, a Sequence of u8.

A std::variant’s variants are named after its alternatives’ types, and its discriminants are their indices, unless KLADDE_VARIANT(V, "Name", 1, 2, …) pins the discriminants or KLADDE_VARIANT_NAMED(V, "Name", (0, "Circle"), (1, "Poly"), …) also names the variants. Variant names are part of a type’s fingerprint, so a program that shares files with one written in another language names them as that program does: Rust’s Poly(Vec<Point>) is held in C++ as a std::vector<Point>, which would otherwise be named after its type.

A std::vector of elements whose size depends on their value fails to compile, with a message that names kladde::Vector: it is the one place where the plain type would quietly cost what kladde exists to avoid.

Handles

kladde::Mut<T> is the short-lived handle, kladde-rs’s Mut, valid until something is written through a handle that is not itself or made from it. C++ cannot enforce that rule, so it is documented, like iterator invalidation; and since a handle made from another refers to its parent’s place in the sequence, a handle must not be moved while a handle made from it lives.

kladde::Ref<T> is the long-lived handle, to an element of a kladde::List, valid until the element is destroyed, as Values and their positions describes. Each list element is an anchor: it knows its list and its index, and finds its start by asking its list, which asks the anchor of the value that holds it, up to the file’s root. The list finds its own offset inside that value by walking the value’s fields to it, which costs the sum of the sizes of the fields before it, each of which every durable type knows in constant time.

Errors

Opening and creating return kladde::expected<T>, a C++20 stand-in for std::expected<T, kladde::error>, since their failures are ordinary and the caller must handle them, with or without exceptions.

A mutation or a flush fails only when the disk does, and the file is then poisoned. With exceptions, the call throws kladde::exception; without, it calls the handler that kladde::set_error_handler installs and returns, leaving the value as it was, since memory changes only after the store recorded the change.

Flushing

Flushes happen by themselves as the journal fills, and on flush() and close(). An interactive application calls file.flush_if_journal_exceeds(0.5) from its idle callback, so that a flush, and its fsync, falls between gestures; the Inkscape demo does so from a low-priority Glib::signal_idle handler after each change. As in kladde-rs, a write or splice of at least Options::payload_threshold bytes keeps them in payload pages, a flush seals the journal it folds where a reusable page can start the next one, and Options::sync_on_worker lets a flush that a mutation triggered run its fsync and header write on a std::thread of their own, as Transactions and batches describes; it is off by default.

Inside the library

Inside the library, every fallible function returns an expected, and KLADDE_TRY propagates it as Rust’s ? does, so the port of the store follows kladde-rs line by line.

Where kladde-cpp departs from the draft

  • Struct fixed forms are not implemented yet: kladde::Fixed<T> takes scalars and enum class only.
  • kladde::Box<T> reports no fixed size, where kladde-rs’s Box<T> reports T’s: a recursive type reaches itself through a box, and asking would make the compiler instantiate the type inside itself. The fixed size is an optimization of the typed layer, not part of the schema, so files are unaffected; only a std::vector of boxes is refused that kladde-rs would accept.
  • An enum class’s discriminant width in the fixed form is the smallest of 1, 2, 4 and 8 bytes that holds the largest discriminant, as for a Rust enum without #[repr], not the size of the underlying type, which C++ defaults to int.
  • Class hierarchies (kladde::Poly<Base>), debug checking of handles, and reflection are not built yet.
  • The Inkscape demo observes Inkscape’s XML tree rather than replacing it; see the evaluation.
